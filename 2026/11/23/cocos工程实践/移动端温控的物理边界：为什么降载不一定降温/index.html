移动端温控的物理边界：为什么降载不一定降温

Posted on 2026-11-23 In cocos工程实践
从 CMOS 功耗模型与渲染管线推出移动端温控的三条边界：CPU 与 GPU 的能量去向不同、平台功耗墙会让负载与温度解耦、帧率与分辨率是同一个恒等式的两端。

引擎做温控，最自然的设计是：游戏跑得越重，机身越烫；把负载降下来，温度就下来。

这句话在多数时候成立，但它有一个隐含前提——你降掉的那部分负载，恰好是发热的主要来源。而这个前提是否成立，不由策略决定，由芯片和平台决定。

与其从实验讲起，不如先把模型摆出来。下面的三条结论都能从功耗模型和渲染管线推出来，真机数据只是用来验证推论，而不是用来”发现”结论。

零、一个式子

机身温度不直接由帧率或分辨率决定，而由单位时间内芯片翻转的电荷量决定。经典 CMOS 动态功耗：

  • C 不是芯片的总电容，而是当前被激活的那部分——同时翻转的晶体管面积
  • f 是时钟频率，α 是翻转率
  • P_static 是漏电，与温度和工艺强相关

温度是 P 对时间的积分，再被散热能力削掉。所以”降低负载”要真正降温，必须做到一件事：

让 C × f 的乘积变小，而不只是让某些环节变快。

记住这一点，后面的三条边界都是它的推论。

一、推论一：GPU 负载与 CPU 负载的能量去向不同

填充率的能量去了哪

像素填充的成本不在”画了多少个三角形”，而在每个像素都要读改写一次 framebuffer。这意味着：

  • 数据要出片——落到片外 DRAM
  • DRAM 每 bit 的访存能耗，比片上 SRAM 高 1~2 个数量级
  • 而 GPU 是”整块芯片一起拉起来”的：C 是全部流处理器面积

于是填充率主导的负载，C 极大、f 也高，功耗是”面积 × 频率”的量级。

逻辑的能量去了哪

JS 单线程把一个大核压满，情况完全不同：

  • 只有一个核在跑，其余核可以被时钟门控关掉——C 只有一个核的量级
  • 工作集小，绝大部分访存命中 L1/L2，几乎不出片
  • 频繁的短时唤醒，还能被 DVFS 压到较低的电压点

同样是”把帧率从 60 压到 30”，GPU 场景和 CPU 场景的 α·C·V²·f 可以差出数倍。

佐证

六台机器、同一套采集方法，测”负载带来的那部分热量”（T2 − T1：跑场景的稳态温度减空跑稳态温度）：

机型 GPU 场景负载温升 CPU 场景负载温升
红米 K30（低端安卓） +7.5℃ +3.5℃
OPPO 平板 +9.4℃ −0.9℃
小米 15（旗舰） +10.1℃ −0.7℃
华为 Mate 60（鸿蒙） +15.0℃ +3.0℃
苹果 17 / 13 +0.5℃ / +0.9℃ −0.4℃ / —

最干净的一组来自 OPPO 平板：把 CPU 负载翻倍到 2000 个实例化立方体，帧率从 51.7 砍到 26.3fps（比同机 GPU 场景的 30fps 还低），温度却只有 −0.9℃。

帧率掉了一半，α·C·V²·f 几乎没变——因为那部分负载的 C 本来就小。

还有一个更直接的对照，来自红米 K30 同一台机器：

配置 帧率 温升
CPU 负载 + 锁 30fps 28.5 fps +8.6℃
GPU 负载 + 降分辨率 28.0 fps +14.0℃

帧率几乎相同，P 差出一大截。 帧率描述的是”算力是否足够”，不描述”功率有多高”——这是两件事，只是平时被混在一起看。

二、推论二：当固定开销占满功耗预算，负载与温度解耦

手机 SoC 都有功耗墙。这带来一个容易被忽略的状态：

当”与游戏负载无关的固定开销”——系统合成、图形桥接、屏幕刷新、平台侧的高清模式——已经把功耗预算吃满时，芯片处在功耗受限状态。此时：

这背后不是”散热差”，而是平台的功耗分配策略：它优先保证系统合成和显示链路，把剩余预算留给应用。应用侧再怎么省，省出来的也只是剩余预算里的一小段。

佐证

iPhone 17 上，空场景跑到 60fps 就已经是 42.8℃，再加 7 层 GPU 负载，温度仍是 42.8℃——全部轮次的终点跨度只有 0.1℃。

iPhone 13（系统已移除温度接口，改用红外测温枪点测机身背面）呈现同样的形状：空场景 40.1℃、GPU 6 层 41.0℃、CPU 400 立方体 38.7℃，跨度 2.3℃。

值得注意的是最后那个数：CPU 负载比空场景还凉 1.4℃。这不是噪声，而是”负载把调度器推向更省电的频点”的直接表现。

含义

在这类设备上，应用侧的任何降载都换不到温度——因为可削的那部分，根本不在你被分配到的预算里。

这条边界不是靠优化能突破的，它属于平台。

三、推论三：帧率与分辨率是同一个恒等式的两端

这是三条里最有实操价值的一条，因为它解释了一个反直觉现象：只降分辨率，温度几乎不动。

推导

未封顶时，一帧耗时 t 与帧率 f 满足：

降分辨率让 t 变小；如果 f 自由，它会立刻变大来填满时间预算。单位时间内的总工作量：

w(t) 是单帧工作量，随 t 下降而下降。但因为 f 同时上升，W 几乎不变——**α·C·V²·f 也就不变**。

要打破这个循环，只能先把 f 钉死：锁帧之后，t 的下降不再被 f 的上升抵消，W 才真的变小。

佐证

红米 K30，只降分辨率（1.00 → 0.70），帧率自由：

配置 帧率 温升
GPU 基线（1.00） 22.7 fps +14.4℃
只降分辨率（0.70） 28.0 fps +14.0℃

帧率涨了 23%，温度只降 0.4℃——W 守恒，画质白掉。

同一台 OPPO 平板上，把顺序换过来：

配置 温升
GPU 基线 +13.1℃
只限帧 30fps +11.9℃（−1.2）
限帧 30 + 分辨率 0.70 +6.6℃（再 −5.3）

同一刀分辨率，锁帧之前砍不动，锁帧之后一刀砍掉 5.3℃。

华为 Mate 60 上这组数据更完整，也更接近”纯限帧”的极限：

配置 帧率 温升 削掉占比
温控关 41.3 fps +18.0℃ —
只限帧 30fps 29.8 fps +10.0℃ 53%
限帧 30 + 分辨率 0.70 29.8 fps +9.0℃ 60%

限帧一个人削掉了一半多的热量；再降分辨率只多值 1℃。

一个修正项：升采样的开销会改变 w(t)

Mate 60 那”只多值 1℃”，来自它的 FSR：每帧需要按原生分辨率跑两趟 pass，把降分辨率省下的 w(t) 又加了回去。

所以这个恒等式里，w(t) 不只包含被缩放的渲染成本，还包含升采样的固定开销。同一套策略在 OPPO 上值 5.3℃，在 Mate 60 上只值 1.0℃——差的就是这一项。

四、把三条合起来看

温控能动的，只有”负载产热”那一段。而这一段的大小由场景结构和芯片能效共同决定，不由策略决定：

机型 负载温升（T2 − T1）
苹果 17 +0.5℃
苹果 13 +0.9℃
红米 K30 +7.5℃
OPPO 平板 +9.4℃
小米 15 +10.1℃
华为 Mate 60 +15.0℃

同样的”打游戏”，可操作空间差了 30 倍。

这决定了它不是”一个能降温的功能”，而是”一个在特定结构下有效的工具”。所以在工程上，与其默认开启，不如把它做成可判断的：

  1. 降分辨率，帧率明显涨（1.00 → 0.70 涨超过 20%）→ 瓶颈在填充率，可削
  2. 比空项目热 5℃ 以上 → 有可削的空间
  3. 非 iOS 用户反馈发烫 → 真实场景比实验室更准

反例只有一个：什么都不画也烫——这类属于推论二，削每帧固定开销才是正解，降档无用。

一条承诺

因为上述三条边界都不在应用侧手里，所以必须把话说在前面：

开了温控、温度没降下来是有可能的；为了降温降了画质、却没换到温度（误伤）也难以完全避免。

能承诺的只有一条——不会更烫。大概率更凉，但不是 100% 更凉。

五、测试工程

压力测试程序开源在这里，两个负载场景都做了”只在一个维度加成本”的设计，参数可运行时调整，采集口径与本文一致：

https://github.com/MagicXHouse/ThermalStressTest

口径说明：文中温升均为「结束温度 − 起始温度」，起点统一控制在 25~27℃，每轮跑满至稳态；跨机型比较只看”负载带来的那部分”，不比绝对温度。iPhone 13 因系统已移除温度接口，使用红外测温枪点测机身背面表面温度，与其他机型的电池温度不可直接比绝对值，仅表示同一台内部的跨度。
